# Workflow: Add Command

Contents: 1. Stage plan, written into the spec · 2. Options and Input · 2a. Present the plan · 2b. Write the spec · 3. File table · 4. Generate the skeleton, then write the rest · 5. Build and check · Adding a flag to an existing command

Use when a root command exists and the request adds a command or reshapes one, or asks for a plan to do so. A request that only adds a flag or argument to an existing command starts at **Adding a flag to an existing command**, at the end of this file. Plan the stages before writing a plan document or creating any file. A plan that covers several commands holds steps 1 to 2a for each one. The skeleton is generated by `nnscaffold`; the plan decides its flags. Read `references/architecture.md` sections 3, 4, 6, and 7 before step 3, and `references/style.md` before step 4.

Before step 1, read the tool's marker, `<tool>/.nn-cli-architecture`, and the version headings in `references/changelog.md`. When the marker is missing, or the changelog has entries under `## [Unreleased]` or under a version newer than the marker, say once that the tool is behind the architecture and that `Workflows/catch-up.md` lists what to refactor, then continue with this workflow unless the user says to catch up first.

## 1. Stage plan, written into the spec

Decide every row before any file. Each decision is written once: what the spec can hold goes straight into the spec JSON (step 2b), and only behavior the spec can't express goes in prose, as the command's behavior notes. Never write a decision in both. A row with nothing in it is a decision, not an omission: leave its spec key out and write "none" in the notes.

| Stage | Into the spec | Into the behavior notes |
| --- | --- | --- |
| Facts | `facts`: what the inspector reads (tools, files, repository state); a thing that may be absent is optional. `inspector.dependencies`: what it reads through (shell, file system, a path) | how the inspector reads each one |
| Blocking facts | `errors`: one case per fact that stops the command, each with its `message` | the check the inspection interpreter makes for each |
| Findings | `findings`: what is settled before anyone is asked | how the inspection interpreter derives each one |
| Requirements | `requirements`: each input's `value`, its `info` for when it is `.unknown`, its `prompter`, and `optional` when only some runs have it | when each is `.known` (which flag or fact settles it), and when an optional one applies |
| Answers | nothing: generated from the requirements | none |
| Helpers | `helpers`, with `examples` for what each returns or throws | none: the examples are the behavior |
| Context | `context`: every field the resolver needs, and nothing the resolver must look up itself | how the collection interpreter builds it |
| Results | `results`: one case per outcome, with the summary each carries | which resolver step ends in each case |
| Use cases | `useCases`: dependencies and the method signature | the steps of each method body |
| Report | nothing | what the formatter's message says for each results case |

If every requirement is always `.known`, the command uses `NnPassthroughCollector` and `NnPassthroughCollectionInterpreter<Findings>`, its Context is its Findings (the spec has no `context`), and it has no `Collector/` folder.

## 2. Options and Input

If the command takes flags: write each argument, option, and flag into the spec with its help text; the generated `makeInput()` maps them. The behavior notes list only the pairs that conflict (for `validate()`). A flag another command already takes with the same meaning goes in the shared `<Concern>Options` (universal rule 9), not in this command's Options; the spec includes that group through `optionGroups`. Every requirement that a flag can settle names that flag; that is the `flagHint` the collector passes, and the spec sets it with `"flag"` when the names differ. If the command takes no flags, skip this step and state in `discussion` that the command is interactive.

## 2a. Present the plan

Show the user, before step 4 runs:

1. The spec from step 2b and the behavior notes from steps 1 and 2. There is no separate stage table: the spec is the plan.
2. The exact `add-command` invocation, derived from the plan:

| Flag | Derived from |
| --- | --- |
| `<name>` | the command name, kebab-case. Under a group, prefix it with the group's name, `<group>-<name>`: the types get the prefix (`debug-run` gives `DebugRun`) and the command registers as `<name>` (`run`) |
| `--parent` | the group or root the command registers on; the tool's name for the root |
| `--abstract` | the one-line description |
| `--passthrough` / `--no-passthrough` | `--passthrough` when every requirement in step 1 is always `.known`; otherwise `--no-passthrough` |
| `--options` / `--no-options` | `--options` when step 2 lists any flag or argument; otherwise `--no-options` |
| `--inspector-location` | a Core kit name, short (`ConfigKit`) or full (`<App>ConfigKit`), when the inspector's facts belong in a library target (section 5 of `references/architecture.md`); `feature` otherwise. A Kit that does not exist yet is created first with `add-kit` (step 4a) |
| `--inspector` | instead of `--inspector-location`, when an inspector the tool already has gathers the facts from step 1 (often the one its sibling commands share). It is built the same way an existing command builds it, so no inspector is generated |
| `--spec` | the JSON file from step 2b. Pass it whenever step 1 has any rows to fill |

When `--parent` names a group that does not exist yet, the plan also shows the `add-group` invocation that creates it (step 4a).

3. The files the run creates: run the invocation with `--preview` and show its list instead of writing one. When the tool doesn't exist yet (a new project), show it after `cli init` creates the tool. A prompter or helper the spec doesn't create is listed as the `add-prompter` or `add-helper` invocation that creates it, never as a file to write.

## 2b. Write the spec

The spec is the plan's decisions from steps 1 and 2, in JSON. Keep it beside the plan document, which holds the behavior notes, not in the repository. Every section may be left out. A key the tool doesn't know stops the run, naming the key and where it is.

```json
{
  "imports": ["AppCoreKit"],
  "arguments": [{ "name": "version", "type": "String?", "help": "The version to tag. Prompts when omitted." }],
  "options": [{ "name": "bump", "type": "BumpKind?", "long": "bump", "help": "…" }],
  "flags": [{ "name": "dryRun", "long": "dry-run", "help": "…" }],
  "requirements": [
    { "name": "bump", "value": "BumpKind", "info": "Void", "prompter": { "name": "BumpKind", "kind": "single" } },
    {
      "name": "version",
      "value": "String",
      "info": { "name": "UnknownVersion", "fields": [{ "name": "latestTag", "type": "String?" }] },
      "prompter": { "name": "Version", "kind": "input" }
    },
    { "name": "pushAction", "value": "PushAction", "info": "Void", "optional": true, "prompter": { "name": "PushAction", "kind": "single" } }
  ],
  "enums": [{ "name": "BumpKind", "cases": ["major", "minor", "patch"] }, { "name": "PushAction", "cases": ["push", "skip"] }],
  "models": [
    { "name": "TagTarget", "fields": [{ "name": "commit", "type": "String" }, { "name": "createdAt", "type": "Date" }] },
    { "name": "PushState", "cases": ["pushed", { "name": "behind", "values": [{ "name": "count", "type": "Int" }] }] }
  ],
  "knownTypes": ["GitClient"],
  "helpers": [
    {
      "name": "VersionBump", "role": "builder", "stage": "inspection",
      "params": [{ "name": "latestTag", "type": "String?" }, { "name": "bump", "type": "BumpKind" }], "returns": "String",
      "examples": [
        { "given": { "latestTag": null, "bump": ".minor" }, "expect": "0.1.0" },
        { "given": { "latestTag": "1.2.3", "bump": ".major" }, "expect": "2.0.0" }
      ]
    },
    {
      "name": "Version", "role": "validator", "stage": "collection",
      "params": [{ "name": "version", "type": "String" }, { "name": "tagNames", "type": "[String]" }],
      "examples": [{ "given": { "version": "1.x", "tagNames": "[]" }, "throws": ".invalidVersion(version: \"1.x\")" }]
    }
  ],
  "useCases": [
    {
      "name": "CreateTag",
      "property": "tagCreator",
      "dependencies": [{ "name": "shell", "type": "any Shell", "from": "context.shell" }],
      "method": { "name": "create", "params": [{ "name": "version", "type": "String" }], "throws": true }
    }
  ],
  "context": [{ "name": "version", "type": "String" }, { "name": "target", "type": "TagTarget" }, { "name": "pushAction", "type": "PushAction?" }],
  "results": [{ "case": "tagged", "summary": [{ "name": "version", "type": "String" }, { "name": "pushed", "type": "Bool" }] }, { "case": "dryRun" }],
  "facts": [{ "name": "tagNames", "type": "[String]" }, { "name": "workingTreeIsClean", "type": "Bool" }],
  "findings": [{ "name": "headCommit", "type": "String" }, { "name": "dryRun", "type": "Bool" }],
  "errors": [
    { "name": "notAGitRepository", "message": "Run this inside a git repository." },
    { "name": "invalidVersion", "values": [{ "name": "version", "type": "String" }], "message": "'{version}' isn't a version. Use major.minor.patch, such as 1.4.0." }
  ]
}
```

- **Types** are written as in Swift. An optional property's `?` is part of its type, and a flag's Input field is `Bool`. Every Input field and fact needs a value for the generated tests. Optional types, `String`, `Bool`, `Int`, `Date`, and arrays get an empty one; any other type needs an entry in `testValues`.
- **`long`** is the flag's name. Leaving it out uses the property name in kebab-case.
- **`imports`** names the modules the field types come from, including the module of a factory type a dependency uses (`FileSystem` from the tool's file kit). A file also imports `Foundation` when its own fields use `Date`, `URL`, `UUID`, or `Data`, and the command does when a dependency's `from` builds one (`Date()`). Helper files get the same imports, and helper tests get them when they have examples.
- **`optionGroups`** includes a shared `<Concern>Options` in this command: `{ "name": "scaffold", "type": "ScaffoldOptions", "input": "ScaffoldInput" }` adds `@OptionGroup var scaffold: ScaffoldOptions`, an Input field `scaffold: ScaffoldInput`, and `scaffold: scaffold.makeInput()` in `makeInput()`. Deriving the `<Concern>Settings` from it is the inspection interpreter's job, written in step 4b.
- **`testValues`** maps an Input field or fact name to the Swift expression the generated tests use for it, for a type with no empty value: `{ "tool": "makeToolFacts()", "scaffold": "makeScaffoldInput(previewRequested: false)" }`. The expression is written into the tests as given, so a factory it calls must exist in `Tests/<tool>Tests/Shared/`. A key that names no Input field or fact stops the run.
- **Requirements** are asked in the order listed. A requirement with a `prompter` gets a new prompter of that kind (`input`, `single`, or `multi`). Its options are filled when the value type is one of the spec's enums. A prompter the tool already has is named with `{ "existing": "<Type>", "method": "<method>" }`: the collector gets its property, built with `.init(picker: picker)`, and asks with `requirements.<name>.ask(<name>Prompter.<method>)`, and no prompter file is created. A requirement without a `prompter` gets a placeholder ask. `"optional": true` marks a requirement that only some runs have (it applies on one branch of a decision): it becomes `NnRequirement<…>?`, the collector asks it with `requirements.<name>?.ask(...)`, and the test factory takes it as optional.
- **`info`** is either a type that already exists, written as in Swift (`Void`, `[String]`), or an object with a `name` and `fields`. The tool writes the object as a struct nested in `<Feature>Requirements`, and every other file names it `<Feature>Requirements.<Name>`.
- **A prompter's `flagHint`** names the option or flag that has the requirement's name, or the argument as `<name>`. When the input that supplies the value has a different name, set `"flag"` on the prompter to the hint, such as `"<version>"` or `"--executable"`.
- **`facts`** fill the inspector's `Facts`, with `public` fields and a `public init` when the inspector lives in a Kit, and the facts test factory, which takes every fact. They are ignored with `--inspector`, which generates no inspector.
- **`inspector`** gives a new feature inspector its `dependencies`, in the same `{ name, type, from }` shape as a use case's: each becomes a stored property and `init` parameter, `makeWorkflow()` builds the inspector from the `from` expressions, and the inspector test's `makeSUT` takes them. A spec with inspector dependencies puts the inspector in the feature folder; `--inspector` or a Kit `--inspector-location` stops the run, so write a Kit inspector's dependencies by hand.
- **Enums** become `String, CaseIterable` files in `Models/`. One used as an argument or option type also conforms to `ExpressibleByArgument`.
- **`models`** are every other type the command defines: a model with `fields` becomes a `Sendable, Equatable` struct, and one with `cases` becomes a `Sendable, Equatable` enum whose cases are names or `{ "name", "values" }` objects with associated values. Each is written to `Models/<Name>.swift`.
- **`helpers`** are the command's interpreter helpers, written with their tests to `Interpreters/<Stage>/` exactly as `add-helper` writes them: `name` without the role suffix, `role`, `stage`, and the `params`, `returns`, and `throws` the `add-helper` flags take. Put every helper the plan names here instead of running `add-helper` for each.
- **`examples`** on a helper become its tests. Each example gives one value for every parameter in `given` (`value` when the helper has no `params`) and exactly one of `expect`, the return value, or `throws`, the `<Feature>Error` it throws (the helper needs `"throws": true`, or the validator role). For a `String` or `String?` parameter or return type, a JSON string is the text itself: `"main"` becomes `"main"` in the test, quoted and escaped for you. For any other type, a JSON string is Swift source written out as given: `".behind"` an enum case, `"[]"`, `".invalidVersion(version: \"1.x\")"`. JSON numbers and booleans are written as they are, and `null` becomes `nil`. The `expect` examples become one `@Test(arguments:)` over a typed `examples` list and the `throws` examples another, so the helper's tests exist before its body. Each starts with `.disabled("nnscaffold: implement <Helper>.<method>, then remove this trait")`, so the stub's `fatalError` can't crash the test run; the report's placeholder search lists it. Write each helper body, then remove the trait so its examples run. A helper with examples can't have a parameter named `expected`, since the tests use that name for the result. A helper without examples gets the `makeSUT`-only test file.
- **`useCases`** are the command's use cases, written with their tests to `UseCases/<Name>UseCase.swift`. `name` leaves off the `UseCase` suffix, and `property` is the agent noun the resolver holds it as (`tagCreator`). Each dependency becomes a stored property and `init` parameter, and `from` is the expression `makeWorkflow()` passes for it (`context.shell`, or a store built in `makeWorkflow()`). `method` has a `name`, `params`, `returns`, and `throws` and `async` flags; its body is the stub left to write. The resolver gets a stored property and `init` for every use case, `makeWorkflow()` builds each one, and the resolver test's `makeSUT` takes them.
- **Every type the spec names must exist.** A type counts when it is a Swift or Foundation built-in, a factory product (`Shell`, `FileSystem`, `Directory`, `CommandLinePicker`, `ProgressDisplay`), one of the spec's enums or models, a nested Info type, one of the feature's generated types, a type declared in the tool's target or its Core package, or listed in `knownTypes`. List a type from another package (`GitClient` from a dependency) in `knownTypes`. Any other type stops the run, naming each one, so the build stays green after generation.
- **`context`** fills the resolver's nested `Context` struct. A passthrough command has no `context`, because its Context is its Findings.
- **`results`** turns the resolver's `Results` into an enum with one case per entry. `case` names it, and a `summary` gives it a payload: `"case": "tagged"` with a summary becomes `case tagged(TaggedSummary)` plus a nested `struct TaggedSummary`, and a case without one is a plain case. The formatter gets a `switch` with a stub in each arm, so only the message text is left. The workflow tests' mock resolver returns a case without a summary, or one whose summary fields all have empty values; when no case qualifies, the run stops.
- **`errors`** become the cases of `<Feature>Error`. A `message` is the case's `errorDescription`, written as plain text with `{name}` for each value it shows; every placeholder must name one of the case's `values`. A case without a `message` keeps a placeholder.
- **The spec settles two flags.** Requirements or context make the command collecting, and arguments, options, or flags make it take Options. Passing `--passthrough` or `--no-options` against them stops the run.
- Any conditional skip in the collector stays out of the spec and is written in step 4b.

## 4. Generate the skeleton, then write the rest

Before writing any code, read `references/style.md` completely and `WorkflowReference.md` in the NnArgumentParser skill.

### 4a. Generate

When `--inspector-location` names a Kit the Core package does not have yet, create it first from the same folder:

```
nnscaffold cli add-kit <Name> --[no-]testing-library (--dependency <Kit> ... | --no-dependencies) [--header]
```

`add-kit` adds the `<App><Name>Kit` library, its `<App><Name>KitTests` target, and with `--testing-library` an `<App><Name>Testing` library to `<App>Core/Package.swift`, writes a starter file for each, and adds the test bundle to the `AllUnitTests` test plan when the folder has an `.xcodeproj`. Pass `--dependency` once per existing Kit the new one uses (`FileKit` or the full name), or `--no-dependencies`; the test target picks up each dependency's `Testing` counterpart on its own. It does not link the Kit to the tool's executable target: add `<App><Name>Kit` to that target's dependencies in the tool's `Package.swift`. Never add Kit targets to the Core manifest by hand.

When `--parent` names a group that does not exist yet, create it first:

```
nnscaffold cli add-group <name> --parent <parent> --abstract "<abstract>" [--header]
```

`add-group` writes the group command (a `ParsableCommand` with only `configuration`) and registers it on its parent. Never write a group by hand.

From the repository root (the folder holding the `.xcodeproj`), run the invocation from step 2a with every flag passed:

```
nnscaffold cli add-command <name> --parent <parent> --abstract "<abstract>" --[no-]passthrough --[no-]options (--inspector-location <feature|CoreKitName> | --inspector <TypeName>) --spec <file.json> [--header]
```

A missing flag makes the tool prompt, and without a terminal it fails. Add `--preview` to see the files and the parent edit without writing. Pass `--header` to every `nnscaffold` command in this workflow when the project's existing Swift files have a header comment (`references/style.md`); without it, files get none. If `nnscaffold` is not installed, stop and tell the user to install it with `brew install nikolainobadi/nn/nnscaffold`; never install it yourself or write the skeleton files by hand.

The tool creates the stage files from the file table (`Command/`, `Workflow/<Feature>Workflow.swift`, `Workflow/<Feature>Error.swift` as an empty enum with its `LocalizedError` extension, the inspector or its `Extensions/` conformance, `Models/`, both interpreters, `Collector/` and its models, `Resolver/` and its models, `Formatter/`), adds `<Feature>Options` and `<Feature>Input` with `--options`, and registers the subcommand on the parent's `configuration`. Each stage body is a `fatalError("nnscaffold: implement …")` stub; the tool prints a search that lists them.

With `--spec`, the tool also fills in from the spec:
- `<Feature>Options` (properties and `makeInput()`) and `<Feature>Input`;
- Requirements with their nested Info structs, Findings, and the collector's `Answers`;
- the inspector's `Facts`, and its dependencies with their construction in `makeWorkflow()`;
- an `@OptionGroup` for each option group;
- the error cases, each with its message, or a placeholder when it has none;
- the resolver's `Context` and `Results` with each case's summary, and the formatter's `switch` over every results case;
- the enums and models;
- the helpers, each with its signature, and with parameterized tests from its examples;
- the use cases with their tests, the resolver's use case properties and `init`, and their construction in `makeWorkflow()`;
- the collector's prompter properties and `.ask` calls, in spec order, and each new prompter with its tests; an existing prompter is asked but not created;
- test factories that take every field.

With `--inspector`, the command, workflow, interpreters, and tests name the existing inspector and its `Facts`, and no inspector files are generated. The workflow tests call the inspector's existing facts factory from `Tests/<tool>Tests/Shared/`, and no second one is written.

Reusing an inspector puts it in a second feature, so move it to `Shared/` right after generating (`references/architecture.md` section 7): `Extensions/<Inspector>+NnCommandInspector.swift` for a Kit inspector, `Inspector/<Inspector>.swift` otherwise, into the `Shared/` of the closest folder holding both features. The same goes for a spec prompter a second command needs: move it to `<Group>/Shared/Prompters/` or `Shared/Prompters/` with its test file, and change its `info` parameter from one feature's Info type to the plain values it uses (`tools: [DebugTool]`).

When the tool has a test target (`Tests/<tool>Tests/`), the tool also creates the command's test files there, in folders that mirror the feature folder: tests for the inspection interpreter, resolver, formatter, and workflow; for the collection interpreter and collector unless the command is passthrough; for the inspector when it stays in the feature folder; for the command itself when the project has a Core package; and `Shared/TestFactory+<Feature>.swift`. Each test file holds an empty test struct and its `makeSUT`, and helper example tests start disabled, so `swift test` passes before any test is written. The report lists them under `Tests to write:`. Without a test target, no test files are created and the report says so.

### 4b. Write the behavior notes

What is left is what the behavior notes hold. First, conflicting flags in `validate()`, and anything the spec left out (a helper, prompter, or use case it did not create, an error message it did not give). Then replace each stub, following the stage order: the inspector's reads, the inspection interpreter's checks and derivations, the collector's asks for requirements without a prompter and any conditional skip, the collection interpreter's Context, the resolver's steps and each use case's method body, the formatter's message for each results case, and anything `makeWorkflow()` builds beyond the use cases. Write each helper body against its example tests. Without a spec, write the error cases, the Options flags and Input fields, the model fields, the models, and the resolver's Context and Results by hand first.

Prompters, interpreter helpers, and use cases are never written by hand:

```
nnscaffold cli add-prompter <Value> --feature <Feature|<Group>/Shared|shared> --kind <input|single|multi> (--requirement <field> | --no-requirement) [--header]
nnscaffold cli add-helper <Name> --feature <Feature|<Group>/Shared|shared> --role <detector|validator|classifier|builder> --stage <inspection|collection|shared> [--param <name:Type>]... [--returns <Type>] [--throws] [--header]
nnscaffold cli add-use-case --feature <Feature> --spec <file.json> [--preview] [--header]
```

- **`add-prompter`** reads the `Value` and `Info` types from the requirement field. When the value is a `String`, `CaseIterable` enum, it fills in the options, the `displayName` switch, a `flagHint` naming the Options flag and its values, and the tests. Only the prompt text is left as a placeholder. It prints the `.ask` line to add to the collector.
- **`add-helper`** writes `enum <Name><Role>` with a stub that compiles, and its test file. The stub's verb comes from the role (`detect`, `validate`, `classify`, or `make`), and its signature from the flags: each `--param name:Type` is a parameter (one `_ value: String` when there are none, and a single parameter has no label), `--returns` is the return type, and `--throws` makes it throw. A classifier or builder needs `--returns`; a detector without it returns its first parameter's type as an optional; a validator always throws. Pass the signature the plan decided, so the stub and its call site need no edit. `Foundation` is imported for `Date`, `URL`, `UUID`, or `Data`; a type from a Kit needs its import added. A feature's helper goes in `Interpreters/Inspection`, `Interpreters/Collection`, or `Interpreters/Shared` by stage. A shared location with loose helpers takes no `--stage` other than `shared`; one split into stage folders takes any stage, and asks for it when `--stage` is omitted.

- **`add-use-case`** adds the use cases in a spec file to one command; see **Adding a use case to an existing command** below.

All three write the test file in the mirrored test folder.

The inspector and resolver stubs are generated synchronous. When either awaits anything (an async read, an async use case), change its signature to `async throws` before writing the body. If the command needs a seam the factory does not vend yet (an async shell), add it in the five places listed in section 2 of `references/architecture.md` before writing the use case that takes it.

## 5. Build and check

Run `swift build`. Walk the Don't list in `SKILL.md` against the new feature folder and fix what fails. When the request includes tests, write them into the files listed under `Tests to write:` and run `swift test`; otherwise leave those files as generated and name them in the report as tests still to write. Report the files created and the command's invocation.

## Adding a flag to an existing command

Check first whether another command already takes this flag with the same meaning. If one does, the flag belongs in a shared `<Concern>Options` (universal rule 9): add it there, or create the group and move the existing copy into it, then add the derived field to `<Concern>Settings` and read it where it is used. Otherwise, classify the flag by universal rule 14 in `SKILL.md`, then touch only the files its kind lists.

- **Mode** (it changes which inspector runs or which set of questions the command has): stop. Plan a new command with steps 1 to 5, under a group with its sibling when they belong together.
- **One-step value** (no interpreter asks for it; one step of the work uses it): `<Feature>Options`, with its `validate()` when the flag conflicts with another; `<Feature>Input`; the inspection interpreter's handoff into `<Feature>Findings`; the collection interpreter's handoff into the resolver's `Context`; and the resolver or use case that uses it. A passthrough command has no collection interpreter, and its Context is its Findings.
- **Promptable value** (asked for when the flag is omitted): `<Feature>Options`; `<Feature>Input`; `<Feature>Requirements`, with its `Info` type; the inspection interpreter, which makes it `.known` from the input or `.unknown(Info)`; a prompter from `nnscaffold cli add-prompter` (step 4b); the collector's `.ask` line that `add-prompter` prints; the collection interpreter; the resolver's `Context`; and the resolver or use case that uses it. A passthrough command becomes collecting, which is a reshape.

A change that touches a file outside its kind's list is a reshape: plan it with steps 1 to 5. Then run step 5 against the feature folder.

## Adding a use case to an existing command

A use case the resolver needs after the command exists comes from `nnscaffold cli add-use-case`, never by hand.

1. Write a spec file that holds a `useCases` list, in the same shape as step 2b: `name` without the `UseCase` suffix, `property` as an agent noun, each dependency's `{ name, type, from }`, and the `method`'s signature. It may also hold `imports` and `knownTypes`. Any other section stops the run, because those belong to `add-command`. One file can list several use cases for the same command.
2. Run it with `--preview` and show the list as the plan.
3. Run it without `--preview`.

Every use case is checked before anything is written. The run stops, writing nothing, when:
- a name or property is invalid or repeated;
- a type is neither declared in the tool nor listed in `knownTypes`;
- a new file name already exists anywhere in the target;
- the resolver already has a property with a new use case's name.

Each use case and its test file go in the feature's `UseCases/` folder and its mirrored test folder. Then the run checks three things:
- the resolver is still exactly what `nnscaffold` generates: `struct <Feature>CommandResolver { }`, or its generated properties and `init`;
- `makeWorkflow()` has exactly one `resolver: .init(...)` line, whose labels are those properties in order;
- the resolver tests' `makeSUT` is still the generated one.

When all three hold, the run adds every new property, `init` parameter, construction argument, and `makeSUT` parameter, plus `let context = <Root>.makeContext()` at the top of `makeWorkflow()` when a new dependency reads `context` and the command has no such line. Otherwise it changes none of them and prints the lines to add, grouped by file. Whitespace counts, so even a reformatted line takes the print path.

Then write each use case's method body and call it from the resolver, and run step 5 against the feature folder.
