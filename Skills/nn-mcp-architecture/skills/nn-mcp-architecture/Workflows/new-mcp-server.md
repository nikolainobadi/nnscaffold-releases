# Workflow: New MCP Server

Use when no `Package.swift` with an executable target depending on MCPServerKit exists, or the request is to start a server from nothing. Produces a package with its entry point, the first feature and capability, and a registered server. Every generated file comes from `nnscaffold`; none of them is written by hand.

## 1. Settle the inputs

From the request, fix:

- the server name: PascalCase letters and digits, such as `TodoServer`. It becomes the package folder and the executable.
- where it goes: run from the folder that should hold `<Name>/`. With one `.xcodeproj` there, the package is also added to that project, unlinked. With none, it stands alone. With two or more, the command stops, so choose another folder.
- the first feature and the tools it needs: a feature is one domain (rule 4).

Ask only for what the request leaves open.

## 2. Create the server

Run with the name passed:

```
nnscaffold mcp init <Name> --non-interactive [--header]
```

Files get no header comment unless you pass `--header`. Pass it when the user wants headers, or when the surrounding project's Swift files have them. With it, each file gets a header signed with the git `user.name`, and the command stops if none is set.

It creates:

- `<Name>/Package.swift`, depending on MCPServerKit from 0.1.1 and ending with a `for target in package.targets` loop that adds `.treatAllWarnings(as: .error)` to every target.
- `<Name>/Sources/<Name>/Main/<Name>.swift`, holding `@main` and an empty `makeFeatures()` (rule 1). Keep its signature as generated.
- `<Name>/Tests/<Name>Tests/Shared/ToolResultText.swift`, holding the shared `extractText`.

It then installs the MCPServerKit and nn-mcp-architecture skills at project scope, in the folder holding the `.xcodeproj`, or in `<Name>/` for a standalone server. A skill that fails to install is listed in the report and does not fail the command.

If the command fails, report its error and stop. Do not create or repair these files by hand.

## 3. First feature and capability

Follow **Add a feature** below, which ends by routing to [add-capability.md](add-capability.md).

## 4. Startup configuration

If the server needs a path, token, or other required value, resolve it in `makeFeatures()` or a helper it calls (rule 2). A missing value writes one line to stderr and exits 1, naming what to set. Skip this step when nothing is required.

## 5. Build

Run `swift build` in the package. Fix what fails, then check the structure against the Don't list in `SKILL.md`. Write tests only when the request includes them.

## Add a feature

Use when a server exists and needs a new domain, or as step 3 of a new server. Fix the feature's name from the request: PascalCase letters and digits, such as `Recipes`, naming one domain (rule 4). Run from the package folder, or from the folder directly above it:

```
nnscaffold mcp add-feature <Feature> --non-interactive [--server <folder>] [--header]
```

Pass `--server` when the folder holds several servers. Pass `--header` under the same conditions as step 2.

It creates, under `Sources/<Name>/Features/<Feature>/`:

- `Feature/<Feature>Feature.swift`, holding `module(using backend:)` and an empty `capabilities` list.
- `Shared/<Feature>Backend.swift`, the feature's one `Sendable` backend (rule 6).
- `Shared/<Feature>ToolError.swift`, with a domain and one starter case, `operationFailed` (rule 7).

It also adds `<Feature>Feature.module(using: <Feature>Backend())` to `makeFeatures()`. Stores and clients the backend needs get built above the `return [` in `makeFeatures()` and passed in that line (rule 1).

The command stops, writing nothing, when `Main/<Name>.swift` has no `static func makeFeatures() -> [FeatureModule] {`. Servers that weren't generated by `mcp init` usually don't have it, and they aren't supported. If it stops, report its error and stop this step. Do not reshape `Main` or write the feature's files by hand to get past it.

Then follow [add-capability.md](add-capability.md) completely for each read or write surface. If that file can't be read, say so and stop this step.

## Register the server

Use when the request is to register a server with a client, or as the last step of a new server when the request names a client. The steps below are for Claude Code. For any other client, say that this skill doesn't cover it and give the executable's path.

1. In the package, run `swift build -c release`. The executable is `.build/release/<Name>`.
2. Register it with its absolute path, at user scope:

   ```
   claude mcp add -s user <Name> <absolute path to .build/release/<Name>>
   ```

   Pass each required value from step 4 as `-e KEY=value` before `<Name>`.
3. Run `claude mcp list` and confirm the server shows as connected. If it doesn't, run the executable directly: a missing configuration value prints its one line to stderr.

A client picks up the server in its next session. Don't register it at project scope unless the request says to.
